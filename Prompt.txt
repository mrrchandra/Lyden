0. How to Read This Prompt
This is a specification, not a script. It tells you what to build, why each piece exists, and what to avoid. It deliberately leaves implementation details open so you can choose the best tools, patterns, and simplifications for the target scale.

Read the entire document before writing code. Then propose a plan, a repo structure, and a milestone breakdown. Wait for approval before implementing. Build in small, testable increments. Do not attempt to implement everything in one pass.

When you encounter ambiguity, prefer simplicity over cleverness, working code over optimal code, and clear structure over dense abstractions. When in doubt, ask.

1. Mission
Build a from-scratch language model that combines four architectural ideas that are individually proven but rarely co-trained:

State Space Model (SSM) backbone for linear-time, constant-memory sequence processing

Hybrid attention islands (sparse + compressed + local) for precise recall

Mixture-of-Experts (MoE) feed-forward layers for knowledge capacity without proportional compute

CLM-style editable context memory that lives in RAM and is managed by the model itself

The goal is not to beat frontier models. The goal is to build a small, clean, well-documented implementation that demonstrates the architecture works at 100M–500M scale on a single GPU, and that can be scaled up later without rewriting the core.

This is a research and engineering project. Correctness, clarity, and reproducibility matter more than raw benchmark numbers.

2. Non-Negotiable Constraints
These are hard requirements. Do not violate them without explicit approval.

Framework: PyTorch. Nothing else. Not TensorFlow, not JAX, not Rust, not BunJS. The ecosystem for SSMs, MoE, and sparse attention is PyTorch-native.

Scale: The default configuration must train a ~100M–500M parameter model on a single consumer GPU. Provide configs for 100M, 250M, and 500M.

Memory system: The CLM memory lives in RAM. It is not a disk-backed store. It is not a vector database. It is not RAG. It is an editable context buffer.

No external retrieval: No FAISS, no Chroma, no Pinecone, no LanceDB, no external index. The memory is the context.

Reproducibility: Every training run must be seedable and reproducible. Log configs, seeds, and environment.

No magic: No hidden dependencies on pretrained checkpoints unless explicitly configured. The model must be trainable from random initialization.

3. Architectural Overview
The model is a stack of repeating blocks. Each block is either a Mamba block or an Attention block, interleaved at a configurable ratio. Every block is followed by a feed-forward network, which may be dense or MoE.

The default interleaving pattern is 1 Attention : 3 Mamba (Jamba-style). This means for every 4 layers, 1 is attention and 3 are Mamba.

The default feed-forward configuration is:

Mamba blocks use dense FFN

Attention blocks use MoE FFN

This is a deliberate choice: attention layers are where precise recall happens, and MoE is where knowledge capacity is added. Mamba layers stay lean and fast.

4. Component Specifications
4.1 Input Stage
Token Embedding

Standard learned embedding table.

Vocabulary size: 32K default, configurable.

Embedding dim: 768 default for 250M config.

Weight tying between embedding and LM head is enabled by default. This saves parameters and is standard practice.

Positional Encoding

Do not use learned absolute positional embeddings. Mamba handles position implicitly, and attention islands need position information.

Use Rotary Position Embeddings (RoPE) applied only to the attention blocks. Mamba blocks do not need RoPE.

RoPE base frequency: 10,000 default. Expose as config.

Why this matters: Mamba's recurrence already encodes order. Adding absolute positional embeddings would be redundant and could hurt long-context generalization. RoPE on attention layers gives them the position awareness they need without interfering with the SSM's dynamics.

4.2 Mamba Block (SSM Core)
This is the workhorse of the model. It handles the bulk of sequence mixing.

Requirements:

Use a selective SSM (Mamba-2 style preferred, Mamba-1 acceptable).

Support both training (parallel scan) and inference (recurrent) modes.

Support variable sequence lengths without padding.

Expose d_state, d_conv, expand as config parameters.

Implementation guidance:

You may use the official mamba-ssm package if it installs cleanly and supports your CUDA version.

If mamba-ssm is not viable, implement a minimal Mamba block yourself using PyTorch. Correctness matters more than speed for the first version.

A pure-PyTorch reference implementation is acceptable as a fallback. It will be slower but easier to debug.

Dense FFN after Mamba:

Standard 2-layer MLP: Linear(dim, 4*dim) → GELU/SiLU → Linear(4*dim, dim)

Use SwiGLU if you want a modern activation, but plain GELU is fine.

Include dropout (default 0.0 for pretraining, configurable).

Do not:

Do not add MoE to Mamba blocks in the default config. Naive MoE on Mamba projections is known to fail. Keep Mamba dense.

Do not add attention to Mamba blocks. They are separate block types.

4.3 Hybrid Attention Block
This is the precision instrument. It handles exact recall and long-range dependency resolution.

The attention block has three parallel branches combined by a learned gate, plus a GQA projection for the KV cache.

Branch 1: Sliding Window (Local)

Each token attends to the previous W tokens (default W = 512).

Cheap, captures local structure.

Use a standard sliding-window attention kernel. If none is available, mask a full attention computation. For long sequences, prefer an efficient kernel.

Branch 2: Compressed Global (Summary)

Maintain a set of G learnable "global summary" tokens (default G = 64).

These tokens are updated via cross-attention with the sequence, and in turn provide global context to every token.

This is inspired by SCOUT-style compressed segment representations and set-based global attention.

Implementation: a small set of learnable embeddings that attend to the sequence, and the sequence attends back to them.

Branch 3: Selective Fine-Grained (Indexer)

A learned indexer scores token importance and selects the top K tokens per query (default K = 256).

Only those K tokens are attended to.

This recovers precise recall of important tokens without full quadratic attention.

This is inspired by NSA-style selective attention.

Combination:

Each branch produces an attention output.

A learned gate (small MLP or softmax over branch weights) combines them.

The gate should be conditioned on the query and the current context.

GQA Projection:

Apply Grouped Query Attention to the combined output for KV cache efficiency.

Default: 8 query heads, 2 KV heads. Configurable.

Do not use MLA (Multi-head Latent Attention). It is known to underperform at small scale.

RoPE:

Apply RoPE to queries and keys in all branches.

Share RoPE across branches for simplicity.

Do not:

Do not use full dense attention as the default. It defeats the purpose.

Do not use MLA. It's the wrong tool for this scale.

Do not make the three branches optional at first. Build them all, then ablate.

4.4 MoE Feed-Forward
This is where knowledge capacity lives.

Configuration (default):

32 routed experts

2 shared experts

Top-2 routing

Expert hidden dim: same as dense FFN (4 * dim for SwiGLU, or 8/3 * dim for modern variants)

Shared experts always active, routed experts gated

Routing:

Use a learned router: Linear(dim, num_experts) followed by softmax or sigmoid.

Top-k selection (default k = 2).

Apply load-balancing loss (auxiliary loss) to prevent expert collapse.

Consider an auxiliary-loss-free balancing strategy if you can implement it cleanly (DeepSeek-V3 style). Otherwise, standard auxiliary loss is fine.

Expert implementation:

Each expert is a 2-layer MLP.

Use torch.bmm or grouped GEMM for efficiency if possible.

For the first version, a simple loop over experts is acceptable. Optimize later.

Dropout / capacity:

Optional expert capacity factor. Default: no capacity limit (let all tokens route freely).

If training is unstable, introduce capacity limits and token dropping.

Do not:

Do not put MoE on Mamba blocks in the default config.

Do not use more than 64 routed experts at this scale. It's overkill and harder to train.

Do not skip the load-balancing loss. Expert collapse is the #1 failure mode.

4.5 Output Head
RMSNorm before the LM head.

Linear projection to vocabulary size.

Weight-tied to the input embedding by default.

No bias terms.

Optional: Diffusion Decoder Head

This is a stretch goal, not part of the core deliverable.

If implemented, it should be a separate head that can be enabled via config.

It should be trained with a denoising objective and used for parallel generation.

Do not let this block the core model from working.

4.6 CLM Memory Layer
This is the feature that makes the model "know about you" without retraining weights.

Core principle: The live context buffer is the memory. It lives in RAM. The model can edit it in place.

Interface:

Expose the context buffer as an editable object.

The model can emit edit commands as special tokens or structured output.

Supported operations (at minimum):

READ — retrieve a slice of context

WRITE — append or insert content

REPLACE — replace a span

DELETE — remove a span

SUMMARIZE — compress a span into a shorter form

Commands should be textual and human-readable. Example:

text
<|edit|>REPLACE line 42 with "User prefers Python over JavaScript"<|/edit|>
Execution:

After each generation step, check for edit commands.

Apply them to the context buffer in RAM.

Re-tokenize the affected region if necessary.

Continue generation with the updated buffer.

KV cache handling:

Editing the middle of the context invalidates the KV cache from the edit point onward.

Recompute the KV cache for the affected suffix.

For the first version, a full recompute after each edit is acceptable. Optimize later.

Training:

Zero-shot: the model can use CLM with no training, just prompting. This is the default.

Optional RL: provide a training script for RL-based memory policy learning. This is a stretch goal.

Do not make RL training mandatory. The zero-shot path must work.

Do not:

Do not use disk. The buffer is RAM-only.

Do not use a vector database.

Do not use external retrieval.

Do not make the memory system a separate service. It is part of the model's runtime.

5. Training Pipeline
5.1 Data
Default dataset mix:

99% FineWeb-Edu (or a comparable high-quality web text dataset)

1% Cosmopedia-v2 (or a comparable synthetic textbook dataset)

This mix is proven at small scale (Supra2-Nano).

Tokenization:

Train a BPE tokenizer on a sample of the data.

Vocabulary size: 32K default.

Use a well-tested tokenizer library (HuggingFace tokenizers is fine).

Save the tokenizer with the model checkpoint.

Data loading:

Stream data from disk, tokenize on the fly or pre-tokenize into shards.

Pack sequences to maximize GPU utilization. No padding.

Support variable sequence lengths.

Shuffle at the shard level, not the sample level.

Sequence length:

Default: 2048 tokens for training.

Support up to 8192 for long-context fine-tuning.

RoPE and Mamba both handle variable lengths. Exploit this.

5.2 Optimizer
AdamW with decoupled weight decay.

Learning rate: 3e-4 default for 250M config. Scale down for larger models.

Weight decay: 0.1 for most parameters, 0.0 for norms and biases.

Betas: (0.9, 0.95).

Gradient clipping: 1.0.

Split learning rate (critical):

The "trunk" of the model (embeddings, Mamba blocks, attention projections, routers, norms) should be trained at 0.1× the learning rate of the experts and other fast-learning components.

This is the Mini-AGI trick for reducing catastrophic forgetting and stabilizing training.

Implement this as a parameter group mechanism.

5.3 Schedule
Warmup: 2000 steps, linear from 0 to max LR.

Decay: cosine decay to 10% of max LR.

Total steps: configurable. Default: 100K steps for 250M config on ~10B tokens.

Gradient accumulation: configurable. Default: 4.

5.4 Mixed Precision
Use torch.amp with bfloat16 if supported, otherwise float16 with loss scaling.

Keep the optimizer state in float32.

Keep the Mamba SSM state in float32 to avoid numerical instability.

5.5 Checkpointing
Save checkpoints every N steps (default: 5000).

Save optimizer state, scheduler state, RNG state, and config.

Support resuming from checkpoint.

Keep the last 3 checkpoints by default. Configurable.

5.6 Logging
Log loss, learning rate, gradient norm, throughput (tokens/sec), and memory usage.

Log MoE routing statistics: expert load, routing entropy, number of active experts.

Log attention branch gate values (which branch is being used).

Use TensorBoard or Weights & Biases. Configurable.

5.7 Stability Monitoring
Watch for these failure modes and log early warning signals:

Expert collapse: If one expert receives >50% of tokens, routing is collapsing. Increase load-balancing loss weight.

SSM divergence: If SSM state norms grow unbounded, reduce learning rate or add gradient clipping to SSM parameters.

Attention gate collapse: If the gate assigns near-zero weight to one branch, the model is ignoring that branch. Log gate values and check initialization.

Loss spikes: If loss spikes, check for bad data batches. Consider gradient clipping or LR warmup extension.

7. What We Do NOT Want
7.1 Architectural Anti-Patterns
Do not use full dense attention as the default. It defeats the purpose of the SSM backbone.

Do not put MoE on Mamba blocks in the default config. Naive MoE on Mamba projections fails.

Do not use MLA (Multi-head Latent Attention). It underperforms at small scale. Use GQA.

Do not use learned absolute positional embeddings. Use RoPE on attention layers only.

Do not use a disk-backed memory system. The CLM memory is RAM-only.

Do not use external retrieval (RAG, vector DB). The memory is the context.

Do not use a separate memory service. The memory is part of the model runtime.

Do not use more than 64 routed experts at this scale. It's overkill.

Do not skip load-balancing loss. Expert collapse is the #1 failure mode.

7.2 Engineering Anti-Patterns
Do not write monolithic code. Break everything into small, testable modules.

Do not hardcode hyperparameters. Use configs.

Do not skip tests. Every component needs a unit test.

Do not skip logging. You need to see what's happening during training.

Do not use obscure dependencies. Stick to well-maintained, widely-used libraries.

Do not over-abstract. A small amount of duplication is better than a premature abstraction.

Do not optimize prematurely. Get it working first, then profile and optimize.

Do not skip documentation. If it's not documented, it doesn't exist.

7.3 Process Anti-Patterns
Do not implement everything at once. Build incrementally, test at each step.

Do not skip milestones. Each milestone validates a piece of the architecture.

Do not ignore failures. If something doesn't work, debug it before moving on.

Do not assume. If a design decision is unclear, ask.

Do not over-engineer. Simplicity is a feature.

7.4 Scope Creep
Do not implement the diffusion decoder in the first version. It's a stretch goal.

Do not implement RL training for CLM in the first version. Zero-shot CLM is enough.

Do not implement multi-GPU training in the first version. Single-GPU is enough.

Do not implement distributed inference in the first version. Single-process is enough.

Do not implement a web UI or API in the first version. CLI is enough.

Do not implement multimodal input in the first version. Text only.

These can all be added later. They should not block the core deliverable.
